# Pravaah v0.5 API Security Matrix

This inventory follows every router mounted in `apps/server/src/app.ts:39-50`, including the public root at `app.ts:54-59`. Route path is the fully mounted path. **59 endpoints** were counted. The matrix compresses repeated implementation details; the common controls below apply only where the route row says so.

## Common controls and interpretation

- `Auth: User` means `authenticateRequest`: bearer Authorization header → Clerk identity → active internal-user lookup. `Admin` or `Staff+` then means backend role middleware. `Identity` means Clerk identity only, used by onboarding or invitation workflow logic. `Public` is intentionally unauthenticated.
- `Clinic` means `requireClinicAccess` checks exact internal-user clinic match and clinic active state. `Object` means service logic checks the requested object's clinic/relationship. For clinic lifecycle operations, services enforce Admin and same-clinic ownership even though route middleware omits `requireClinicAccess`.
- All named validation is Zod validation via `validateRequest`; absent from public routes where no inputs exist. All routes have **no application-level HTTP rate limiter identified**. Route “status” is `Reviewed` for source trace; this does not imply penetration-tested runtime behavior.
- Controller files are `apps/server/src/modules/<module>/<module>.controller.ts`; services and repositories are matching module files unless noted. Controller names map directly to function names in the route source. The test column lists nearest existing coverage; absence means no route-specific test was identified in the reviewed set.
- Sensitive output shorthand: `Patient` includes identity/contact, DOB/age, address/location, emergency contacts, clinic notes/history; `Appointment` may include patient/doctor/creator, queue and latest no-show prediction snapshot; `Staff` includes profile/email/role/status; `Clinic` includes settings/address; `Operational` includes availability, queue or aggregate metrics.

## Authorization trace notes

Object-based routes that do not have `clinicId` in their URL (appointment status/activity/reschedule and prediction feedback) rely on service-level object-to-clinic resolution. This is an intentional and appropriate pattern; it must remain tested. Doctor and patient operations with a clinic URL verify the `DoctorClinic` or `PatientClinic` association. Queue reorder validates that the submitted entries form the expected clinic/doctor/date set rather than allowing arbitrary IDs. Clinic lifecycle routes call service-level same-clinic checks despite middleware omission.

No route-level HTTP rate limiter was found. Invitation service limits are specific business controls, not a general API rate limiter. The two list routes flagged SEC-F-01 have no pagination parameters or database `take` bound. Read projections include sensitive patient information; response-size exposure therefore increases with clinic dataset size.

## Audit Purpose

This audit records the current Pravaah route, UI, API, workflow, testing, deployment, and release-readiness state before the v0.3 release. It evaluates actual repository evidence rather than only planned behavior.

The audit covers active frontend routes, mounted route guards, frontend API dependencies, backend route protection, role and clinic isolation checks, workflow consistency, screen states, content wording, basic accessibility evidence, test coverage, and deployment readiness.

This audit does not implement application fixes. Implementation work belongs in separate focused issues. Unverified behavior remains explicitly marked as `Needs verification`, and code inspection is not treated as runtime or production verification.

## Audit Scope

Covered areas:

- protected routes

## Evidence And Verification Method

| Evidence level         | Meaning                                                                |
| ---------------------- | ---------------------------------------------------------------------- |
| Code inspected         | Confirmed from repository code, configuration, tests, or documentation |
| Local runtime verified | Personally tested in a locally running application                     |
| Production verified    | Personally tested against the currently deployed application           |
| Test verified          | Confirmed by an automated test that was actually run and passed        |
| Needs verification     | Could not be confirmed with the available environment or tools         |
| Not implemented        | Repository inspection confirms the expected behavior does not exist    |
| Not applicable         | The route, state, or check does not apply to the current product       |

The strongest available evidence is recorded for each meaningful result. This audit ran source inspection and localhost availability probes only. Automated test files were inspected, but no automated suite was run during this audit.

Not runtime reproduced. Finding is based on code inspection.

### Suggested Follow-Up

Create a focused backend/test issue to define allowed appointment transitions, enforce them in service/repository logic, and cover direct API attempts to skip or reverse non-final states.

## F-005 - Queue Reorder Does Not Preserve Doctor-Scoped Position Sequences

| Field              | Value                                                                                                                                      |
| ------------------ | ------------------------------------------------------------------------------------------------------------------------------------------ |
| Severity           | High                                                                                                                                       |
| Area               | Backend                                                                                                                                    |
| Route or workflow  | `/queue`, `PATCH /api/clinics/:clinicId/queue/reorder`                                                                                     |
| Evidence level     | Code inspected                                                                                                                             |
| Release impact     | Manual queue reorder can collapse per-doctor queue positions into one clinic-wide sequence for the day, violating the release queue scope. |
| Related API        | A-018                                                                                                                                      |
| Existing issue     | Not linked                                                                                                                                 |
| Recommended action | Add a focused backend issue to keep reorder validation and persistence scoped to clinic, doctor, and clinic-local day.                     |

### Expected Behavior

Queue position creation and manual reorder should use the same clinic/doctor/clinic-local-day scope. Reordering one doctor's active queue should not rewrite another doctor's active queue positions.

### Actual Behavior

Booking-time queue creation calls `findHighestQueuePosition` with clinic, doctor, and local-day scope. `queueService.reorderQueue` then fetches all active queue entries for the clinic/day, requires the request to include that whole clinic/day set, and calls `queueRepository.reorderQueueEntries` without a doctor predicate. The repository rewrites those entries into a single `1..N` sequence for the clinic/day.

### Evidence

- `apps/server/src/modules/queues/queue.service.ts`
- `apps/server/src/modules/queues/queue.repository.ts`
- `docs/releases/V0.3_RELEASE_CHARTER.md`

### Steps To Reproduce

Not runtime reproduced. Finding is based on code inspection. A representative scenario is a clinic with active entries for two doctors on the same local day, followed by a manual reorder request that includes all active clinic/day entries and rewrites both doctors' positions as one global sequence.

### Suggested Follow-Up

Create a focused backend/test issue to add doctor-scoped reorder input, validation, persistence predicates, and tests for multi-doctor same-day queues.

## F-006 - Queue Status Lifecycle Allows Non-Final Skips And Reversals

| Field              | Value                                                                                                                            |
| ------------------ | -------------------------------------------------------------------------------------------------------------------------------- |
| Severity           | High                                                                                                                             |
| Area               | Backend / Testing                                                                                                                |
| Route or workflow  | `/queue`, `PATCH /api/clinics/:clinicId/queue/:queueEntryId/status`                                                              |
| Evidence level     | Code inspected                                                                                                                   |
| Release impact     | The v0.3 charter expects invalid queue transitions to fail; current backend enforcement does not fully support that requirement. |
| Related API        | A-017                                                                                                                            |
| Existing issue     | Not linked                                                                                                                       |
| Recommended action | Add a focused backend issue for explicit queue status transition rules and tests.                                                |

### Expected Behavior

The backend should enforce the approved queue lifecycle so unsupported skips or reversals fail consistently, not only through frontend button visibility.

### Actual Behavior

`queueService.updateQueueStatus` rejects updates only when the current queue entry is already in a final state. For non-final entries, `queueRepository.updateQueueEntryStatus` accepts any validated queue status enum and synchronizes the appointment status from that request. A direct API request can therefore move a non-final queue entry backward, such as `CALLED` to `WAITING` or `ARRIVED`.

### Evidence

- `apps/server/src/modules/queues/queue.validation.ts`
- `apps/server/src/modules/queues/queue.service.ts`
- `apps/server/src/modules/queues/queue.repository.ts`
- `apps/server/src/modules/queues/__tests__/queue.service.test.ts`
- `docs/releases/V0.3_RELEASE_CHARTER.md`

### Steps To Reproduce

Not runtime reproduced. Finding is based on code inspection.

### Suggested Follow-Up

Create a focused backend/test issue to define allowed queue transitions, enforce them in service/repository logic, keep appointment synchronization forward-safe, and add tests for direct API attempts to skip or reverse non-final queue states.

## Content Principles

Pravaah content should be clear, direct, respectful, operational, non-medical, non-absolute, human-controlled, honest about implementation status, understandable to clinic staff, and consistent across public and protected routes.

## Approved Product Description

Use:

```txt
Pravaah is a clinic appointment and queue-management platform with explainable, rule-based no-show risk assistance.
```

Do not position Pravaah as hospital management software, an electronic medical-record system, a medical diagnosis system, autonomous clinic AI, a trained prediction engine, a patient portal, or a doctor portal unless future implementation and scope formally change.

## Role Language

Use `Admin` and `Staff`.

Admin controls clinic setup and higher-level operations. Staff manages daily clinic flow. Doctor and Patient are records, not authenticated roles in the current release. Do not imply that patients or doctors can log in.

## Status Language

Use readable labels in UI/content and enum names in technical docs.

| Internal enum | Display label |
| ------------- | ------------- |
| SCHEDULED     | Scheduled     |
| CONFIRMED     | Confirmed     |
| ARRIVED       | Arrived       |
| IN_QUEUE      | In Queue      |
| CALLED        | Called        |
| COMPLETED     | Completed     |
| CANCELLED     | Cancelled     |
| NO_SHOW       | No Show       |
| WAITING       | Waiting       |

Avoid `No-show` and `In queue` variations in new UI unless existing code is being preserved. Prefer `No Show` and `In Queue` for consistency.

## Risk Language

Risk wording must communicate that risk is an estimate produced by deterministic rules, reasons should be visible, risk does not prove future behavior, staff makes the final decision, risk must not shame patients, risk does not provide medical guidance, and risk does not automatically cancel or reorder anything.

Approved examples:

```txt
High no-show risk
This appointment has several risk indicators.
Review the listed reasons before deciding whether follow-up is needed.
```

Avoid:

```txt
This patient will not attend.
AI predicts that the patient will miss the appointment.
Automatically move this patient back in the queue.
Unreliable patient.
```

## Capitalization And Formatting

| Item                | Rule                                                                       |
| ------------------- | -------------------------------------------------------------------------- |
| Page titles         | Title case: `Clinic Settings`, `Add Patient`.                              |
| Navigation labels   | Short title case.                                                          |
| Role names          | `Admin`, `Staff`.                                                          |
| Action labels       | Sentence or title case with a verb and object.                             |
| Status labels       | Title case display labels; uppercase enum names only in technical docs.    |
| Risk levels         | Display as Low, Medium, High or LOW/MEDIUM/HIGH only in technical docs.    |
| Dates               | Use readable dates in UI; use ISO dates in technical records.              |
| Times               | Include timezone context when relevant; use `Asia/Kolkata` in examples.    |
| Phone numbers       | Do not include real phone numbers in docs or screenshots.                  |
| Clinic names        | Use fictional demo clinics.                                                |
| Error codes         | Uppercase monospace, such as `VALIDATION_ERROR`.                           |
| Route paths         | Monospace, such as `/appointments`.                                        |
| API endpoints       | Method plus path, such as `PATCH /api/appointments/:appointmentId/status`. |
| Code identifiers    | Monospace, such as `appointmentService.createAppointment`.                 |
| Issue/PR references | Use `#211` or repository-relative links where possible.                    |

## Form Content

- Use concise visible labels.
- Mark required fields clearly and accessibly.
- Mark optional fields only when helpful.
- Use helper text for format or decision guidance.
- Placeholders may show examples but must not replace visible labels.
- Field validation should be close to the field.
- Form-level errors should explain the operation that failed.
- Server-validation errors should preserve entered values.
- Success messages should appear only after backend confirmation.
- Destructive confirmations must say what changes and whether records remain preserved.
- Cancel wording should distinguish navigation cancel from destructive cancellation.
- Unsaved-change wording should not blame the user.

## Loading Content

Prefer state-specific language:

```txt
Loading appointments...
Loading today's queue...
Saving clinic settings...
Creating doctor...
Booking appointment...
```

Avoid one generic loading message everywhere when the operation is known.

## Empty-State Content

Every empty state should explain what is missing, whether that is normal, what the user can do next, and whether the user has permission to act.

Examples:

```txt
No doctors have been added yet.
Add the first doctor before booking appointments.
```

```txt
No appointments match these filters.
Clear or adjust the filters to view more appointments.
```

## Error Content

| Error type           | Content standard                                                     |
| -------------------- | -------------------------------------------------------------------- |
| Validation error     | Name the field and safe correction.                                  |
| Authentication error | Ask the user to sign in again.                                       |
| Authorization error  | Say the account cannot perform this action.                          |
| Not found            | Say the record could not be found or may no longer exist.            |
| Conflict             | Explain the competing state, such as appointment slot already taken. |
| Network failure      | Say the API could not be reached and offer retry.                    |
| Backend unavailable  | Use safe operational wording; avoid infrastructure details.          |
| Unexpected error     | Apologize briefly, offer retry/contact path if available.            |

Do not expose Prisma internals, database connection details, Clerk secrets, stack traces, raw exception messages, or sensitive patient data.

## Confirmation Content

Use explicit wording for destructive or final actions:

```txt
Cancel appointment
Mark patient as no show
Deactivate doctor
Deactivate patient
```

Explain what will change, whether the action is reversible, and whether related records remain preserved.

## Release-Claim Language

| Claim                        | Meaning                                               |
| ---------------------------- | ----------------------------------------------------- |
| Implemented and deployed     | Available in the production product                   |
| Implemented but not deployed | Present in code but not verified in production        |
| In development               | Work has started but is incomplete                    |
| Planned                      | Approved future work with no completed implementation |
| Intentionally deferred       | Valid work excluded from the current release          |
| Needs verification           | Evidence is insufficient                              |

Do not use `live`, `released`, or `production-ready` without evidence. Documentation can explain evidence, but it is not implementation evidence by itself.

## Screenshot And Demo-Data Rules

Use fake clinic data, fake doctor data, fake patient data, no real phone numbers, no real patient history, no access tokens, no environment secrets, no private database URLs, and no production personal data.

## Content Maintenance

Update this guidance when a role changes, a status changes, a route is added, a new action is introduced, a release is deployed, the risk system changes, or a new feature becomes implemented.

When implementation changes, update the source product/architecture docs first, then workflow evidence, Project Score evidence, and interview/simulation preparation.

# v0.5 accessibility verification — Issue #296

Date: 28 October 2026. Scope: authenticated Admin and Staff clinic workflows. Target: WCAG 2.2 AA. This is an implementation and verification record, not a conformance claim.

## Audit plan and repository baseline

| Area | Inspected implementation | Interaction risk | Available check |
| --- | --- | --- | --- |
| App navigation | `AppLayout`, `Sidebar`, `Topbar`, protected routes | Mobile drawer focus; account menu semantics; narrow header | React Testing Library; source review |
| Appointment booking and management | `AppointmentsPage`, booking form/dialog, status and reason dialogs | Patient lookup, validation focus, filtered row removal | Vitest component and page tests; axe-core component scan |
| Queue | `QueuePage` | Move controls, status actions, live feedback | Existing and new keyboard tests |
| Patients | `PatientsPage`, `PatientForm`, create/profile flows | Field errors and keyboard completion | React Testing Library page tests |
| Staff and settings | `StaffManagementPage`, `ClinicSettingsPage` | Invitation errors, settings labels and save feedback | Staff page tests; source review |

The app uses native inputs and selects, React Router, Clerk, Tailwind, custom dialogs, and a shared modal focus hook. Booking lookup is a **search input followed by a native select**, not an ARIA combobox. It uses `listPatients` with a 20-record limit and a search term; that bounded API remains in place. Queue reordering already has Move Up and Move Down buttons backed by the existing reorder API. Toasts and several page messages already use status or alert semantics. Vitest, jsdom, React Testing Library, and user-event were present; axe-core was added for a scoped structural scan. No end-to-end browser runner was present. The existing [UX findings](../audits/UX_FINDINGS_V0_5.md) identify F-03 as a verification gap and F-10 as a responsive verification gap.

Testing order: shared modal focus and booking/patient errors; filtered appointment updates; queue keyboard controls; navigation and staff; full frontend checks; then authenticated browser, zoom, and screen-reader checks when a legitimate test session is available.

## Test environment and results

- Host: Linux; Google Chrome 156.0.8078.47 is installed. Firefox failed to start because its snap runtime could not write under `/run/user/1000` in this sandbox. Orca 46.1 is installed, but no real screen-reader session was operated or heard.
- Automated: Vitest 4.1.10, jsdom 27, React Testing Library 16, user-event 14, axe-core 4.14.0.
- Browser viewport/zoom: no authenticated browser session; 320 CSS px, 100%, 200%, and 400% zoom **not verified**. No responsive screenshots were captured. CSS/layout findings are source observations only.
- Test account role: Admin and Staff contexts were mocked in component tests. No live Admin or Staff credentials were used. No Clerk permission checks were bypassed for browser testing.
- Axe: the booking form was scanned in jsdom with no reported structural violations. The `color-contrast` rule was disabled only for this scan because jsdom has no rendered color canvas; contrast, reflow, focus visibility, and speech remain manual checks.
- Data: existing synthetic test fixtures only. No production records, invitations, or database writes were used.

Final local checks: `npm run test -w apps/web -- --maxWorkers=2` passed 32 files and 176 tests; `npm run lint -w apps/web` passed; `npm run build -w apps/web` passed TypeScript compilation and Vite production build. No tests were skipped in that run. An earlier default-worker run failed five tests: four were resolved by updating tests for the corrected account semantics and asynchronous staff loading; one onboarding test timed out under concurrent workers and passed in the final limited-worker run. Backend checks were not run because no backend source or contract changed.

## Manual completion checklist

Use a legitimate synthetic Admin account and a separate Staff account in a development environment. Record browser version, viewport in CSS pixels, zoom, assistive technology, and outcomes for each step. Never use live patient records.

1. At 100%, 200%, and 400% zoom and at 320 CSS px, navigate Dashboard, Appointments, Queue, Patients, Doctors, Staff (Admin), and Settings (Admin). Check focus visibility, no obscured controls, horizontal scrolling where intentionally labeled, and no loss of action buttons.
2. With keyboard only, open booking, search for a synthetic patient, select the native patient list using arrow keys, choose doctor/date/slot, submit invalid values, correct errors, and complete a booking. Check loading/result announcements with a real screen reader.
3. Open and close booking, details, reason, confirmation, and patient dialogs using Tab, Shift+Tab, and Escape. Check focus return. Change a status while a filter removes the row and confirm focus reaches feedback while filter and page context remain intact.
4. Move a queue entry up/down with Space and Enter; confirm position, announcement, focus, filters, status actions, and server order. Test first/last/single-entry boundaries.
5. Create/edit a synthetic patient, invite a synthetic Staff identity without sending a real invitation, and save clinic settings in a safe test environment. Confirm errors, required state, save feedback, and Staff role restrictions.
6. Repeat the critical tasks with Orca + Chrome or another supported real screen-reader/browser combination. Record spoken names, roles, errors, status updates, and any interaction dead ends.

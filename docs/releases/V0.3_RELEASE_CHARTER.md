## Purpose Of This Charter

This charter defines the release boundary for Pravaah v0.3. It exists so implementation, issue planning, pull-request review, testing, release readiness, deployment, portfolio claims, and interview explanations all describe the same product state.

Pravaah has several source-of-truth documents that describe product scope, architecture, roles, setup, and contribution rules. Those documents explain the project as a whole. This charter narrows the next release so planned v0.3 work does not quietly expand into a larger healthcare platform, and so unfinished work is not presented as released.

`docs/product/MVP.md` defines the original product boundary. `docs/releases/V0.3_RELEASE_CHARTER.md` defines the v0.3 release boundary.

## v0.3 Release Objective

Pravaah v0.3 should turn the current clinic-side product into a more complete externally accessible and release-governed product by tightening the public product entry, secure onboarding, clinic provisioning, first-run setup, editing workflows, operational polish, authorization hardening, backend reliability, automated testing, release documentation, and deployment evidence.

The release remains focused on the clinic-side Admin and Staff workflow. It must not redefine Pravaah as a hospital ERP, complete healthcare platform, patient portal, doctor portal, autonomous AI system, or trained machine-learning platform.

## Intended v0.3 User Outcome

A successful v0.3 experience should allow this journey:

```txt
Visitor opens Pravaah
    ↓
Understands the product
    ↓
Signs up or signs in using Clerk
    ↓
Backend verifies the Clerk identity
    ↓
New authenticated user enters onboarding
    ↓
User provisions a clinic
    ↓
Clinic and initial Admin are created consistently
    ↓
Admin completes first-run clinic setup
    ↓
Admin creates the first doctor
    ↓
Admin creates the first patient
    ↓
Admin books the first appointment
    ↓
Clinic staff manages appointment and queue workflows
```

Doctor and Patient remain records rather than authenticated users unless a separate approved v0.3 scope change explicitly adds authenticated doctor or patient roles.

## Release Status Vocabulary

| Status          | Meaning                                                           |
| --------------- | ----------------------------------------------------------------- |
| Planned         | Approved for v0.3 but implementation has not started              |
| In progress     | Implementation work has started                                   |
| Completed       | Implementation is complete locally or in the repository           |
| Release-blocked | Work cannot be considered release-ready because a blocker remains |
| Verified        | Acceptance criteria have been tested and evidence recorded        |

Completed does not automatically mean deployed. Verified does not automatically mean released.

Deployment status should be recorded separately as one of:

- Not deployed
- Preview deployed
- Production deployed
- Production verified

## Required End-To-End Release Workflows

### Workflow A - Public Visitor To Authentication

| Field                       | Value                                                                                                                      |
| --------------------------- | -------------------------------------------------------------------------------------------------------------------------- |
| Purpose                     | Confirm unauthenticated visitors can understand Pravaah and start Clerk authentication without seeing protected data.      |
| Starting condition          | Visitor has no Clerk session.                                                                                              |
| Expected steps              | Visitor opens public route -> understands Pravaah -> chooses sign in or sign up -> Clerk authentication begins.            |
| Success outcome             | Public route renders, product claims are accurate, and auth entry points resolve to valid Clerk flows.                     |
| Important failure cases     | Protected data exposed, misleading product copy, broken auth links, invalid redirect, or public route requiring a session. |
| Release evidence            | Browser screenshot or recording, route test output, and deployed URL smoke result.                                         |
| Current verification status | Needs verification.                                                                                                        |

### Workflow B - New Authenticated User Onboarding

| Field                       | Value                                                                                                                   |
| --------------------------- | ----------------------------------------------------------------------------------------------------------------------- |
| Purpose                     | Confirm a Clerk-authenticated user without an internal record is routed into onboarding rather than protected app data. |
| Starting condition          | Valid Clerk session exists and no internal `User` exists for that Clerk identity.                                       |
| Expected steps              | Clerk-authenticated request -> onboarding status lookup -> no internal user found -> user enters clinic onboarding.     |
| Success outcome             | Missing internal user is treated as onboarding state only for onboarding-aware routes.                                  |
| Important failure cases     | Anonymous access accepted, expired auth accepted, protected APIs exposed, generic confusing failure, or redirect loop.  |
| Release evidence            | Backend onboarding test output, frontend routing test output, and manual browser verification.                          |
| Current verification status | Needs verification.                                                                                                     |

### Workflow E - Appointment Lifecycle

### Workflow F - Queue Lifecycle

## Change-Control Rules

- v0.3 scope changes require reviewed documentation updates.
- Newly proposed features are not automatically part of v0.3.
- Architecture changes require updates to architecture source-of-truth documents.
- Database changes require schema, migration, and documentation review.
- Completed work must not be marked verified without evidence.
- Deployed work must not be marked production verified before smoke testing.
- Deferred work should move to post-v0.3 issues.
- Portfolio or README claims must follow actual release status.
